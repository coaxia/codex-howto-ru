# Протокол измерения инженерного цикла

Используйте протокол, чтобы решить, оправдывает ли навык расход контекста.
Сравните модель без навыка, полную версию v0.2 и текущую компактную.
Цель — выявить, улучшают ли инструкции воспроизводимое завершение с контролем
качества, а не доказать разовую победу одного запроса.

Опубликованный начальный эксперимент использует три варианта. В новом наборе
задач с теми же условиями можно сравнить `no_skill`, текущий компактный навык
и один внешний профиль, добавляя изолированные профили при достаточном бюджете.
См. [сравнение сторонних процессов](third-party-workflow-profiles.md).
Не смешивайте внешние профили с опубликованной таблицей начальных результатов
и не объявляйте upstream-проект лучше по одной задаче.

## Гипотеза

Запишите до запуска вариантов:

```text
Для [класса задач] [вариант навыка] улучшит [основной показатель качества]
без неприемлемого роста [времени, токенов, стоимости или вмешательств человека].
```

Выберите один основной показатель качества. Скорость, токены и стоимость
вторичны, пока все варианты не удовлетворяют одинаковой приёмке.

## Три варианта

Используйте три свежие копии одного исходного коммита:

- `no_skill`: условия задачи без указания или установки навыка репозитория;
- `full_skill`: установить и вызвать `engineering-loop` из тега `v0.2.0`;
- `lean_skill`: установить и вызвать текущий `engineering-loop`.

Фиксируйте модель, рассуждения, исходный коммит, интерфейс Codex, песочницу,
инструменты, инструкции репозитория, зависимости и приёмку.
Для каждого запуска записывайте точные модель, уровень рассуждений,
коммит, метку набора инструментов и версию навыка.
`skill_version`: `none` для `no_skill`, `v0.2.0` для полной версии,
выпуск, commit SHA или метка ветки для компактного кандидата.

Не используйте повторно изменённое рабочее дерево и не переносите открытия
между запусками. Меняйте порядок вариантов между задачами, чтобы уменьшить
влияние порядка и обучения оператора.

[Начальное измерение GPT-5.6-sol для backend](../../../examples/measurements/gpt-5.6-sol-backend-boundary-2026-07-31.md)
показывает завершённое сравнение: все варианты прошли, но оба навыка добавили
токены и повторы в узкой задаче. Это прозрачный пример, а не общий вывод о модели или навыке.

[Измерение игры 2048](../../../examples/measurements/gpt-5.6-sol-2048-game-2026-07-31.md)
применяет тот же протокол к средней реализации. Все варианты прошли,
но компактный навык использовал меньше токенов и раньше прекратил браузерное
исследование. Разные направления результатов объясняют необходимость
представительных повторов до изменения правил команды.

## Минимальный эксперимент

До локального вывода о тенденции выполните не менее трёх наборов сопоставимых задач:

1. Backend-дефект граничного ввода.
2. Frontend-поведение, доступность и небезопасный вывод.
3. Ревью инфраструктуры и план усиления защиты.

Для каждого `task_id` выполните каждый вариант.
Держите [критерии практикума](../labs/engineering-playground/rubric.md)
скрытыми до завершения трёх запусков. Если возможно, проверяйте обезличенные
diff и отчёты без знания варианта.

Три набора упражняют протокол, но не доказывают общей производительности.
До изменения правил команды повторите на представительных реальных задачах.

## Показатели

Записывайте качество до эффективности:

| Показатель | Определение |
|---|---|
| `accepted` | Приёмка выполнена без исправления кода человеком |
| `evidence_complete` | Отчёт разделяет подтверждения, невыполненные проверки, предположения и остаточные риски |
| `regression_before_fix` | Для воспроизводимого дефекта проверка падает до реализации и проходит после |
| `focused_checks_passed` | Узкие проверки изменённого поведения проходят |
| `required_checks_passed` | Все применимые обязательные проверки репозитория проходят |
| `actionable_findings` | Уникальные существенные проблемы финального ревью |
| `false_positives` | Замечания, отклонённые оценщиком как неподтверждённые или не требующие действия |
| `retries` | Попытки, не дающие новых подтверждений |
| `iterations_to_green` | Ограниченные build-judge циклы до первой приёмки |
| `first_judge_passed` | Первый заданный оценщик выполнил условие успеха без новой правки |
| `human_corrections` | Вмешательства, меняющие код, тесты, требования или технический шаг |
| `files_read` | Различные прочитанные файлы, если интерфейс надёжно их показывает |
| `files_changed` | Различные изменённые файлы |
| `unexpected_files_changed` | Файлы вне согласованной области |
| `scope_expansions` | Согласованные изменения исходных путей, подсистем, приёмки или внешних систем |
| `human_checkpoints` | Обязательные согласования дизайна, области, разрешений или интеграции |
| `elapsed_seconds` | Время от отправки запроса до отчёта, включая инструменты и ожидание человека |
| `total_tokens` | Сумма входных и выходных токенов, если доступна |
| `total_cost_usd` | Полная стоимость запуска, если доступна |
| `context_noise_lines` | Сырые диагностические строки в основном контексте, не использованные в итоговых подтверждениях |

Задайте приёмку и подсчёт до запуска. Необязательные недоступные измерения
оставляйте пустыми; не оценивайте скрытые токены или стоимость.

Для сравнения профилей создайте [отчёт задачи](../examples/templates/measured-task-receipt.md)
на запуск. Он дополняет устойчивую CSV-схему областью, ревизией процесса
и бюджетами. Существующие CSV-столбцы сохраняются для воспроизводимости начальных сводок.

## Надёжность повторений

Один принятый запуск показывает выполнимость, а не надёжность.
Для каждого класса и профиля повторите независимые запуски одного состояния и сообщите:

- долю приёмки всех попыток, включая остановленные и упавшие;
- долю успеха первого оценщика;
- медиану итераций до успеха среди принятых;
- число последовательных принятых запусков на зафиксированной ревизии.

Выберите число повторов заранее. Не сбрасывайте последовательность после сбоя
и не пропускайте исчерпавшие бюджет запуски. Надёжность сравнима при одинаковых
оценщике, условии успеха, модели, рассуждениях, репозитории и разрешениях.

## Запись и сводка

Скопируйте [CSV запусков](../../../examples/measurements/engineering-loop-runs.csv)
и добавляйте строку на запуск. Сохраните заголовок, используйте `true` / `false`
для наблюдаемых логических полей. `accepted` и `evidence_complete` обязательны.
Остальные недоступные или неприменимые поля пусты; примечания с запятыми
заключайте в кавычки по CSV-правилам.

Из корня оригинального репозитория:

```bash
python3 scripts/summarize_engineering_loop.py \
  examples/measurements/engineering-loop-runs.csv
```

Сводка сначала показывает доли качества, затем медианы и полноту трёх вариантов.
Она не сводит всё к одному баллу.

## Правило решения

Сохраняйте навык для измеренного класса, только если:

1. Он улучшает корректность, безопасность, подтверждения или уменьшает переделки; либо
2. Даёт повторяемый командный формат или предметное правило, отсутствующее в задаче и контексте;
3. Рост времени, токенов или стоимости оправдан пользой;
4. Результат повторяется на представительных наборах.

Предпочитайте компактный навык при сохранении качества полной версии и меньших
токенах, задержке или повторах. Выбирайте отсутствие навыка при одинаковом
качестве и издержках обоих навыков. «Качественнее, но медленнее»,
«быстрее, но менее надёжно» и «различий не наблюдалось» — допустимые выводы.

Для внешнего профиля сохраняйте минимальный набор upstream-компонентов,
давший измеренный выигрыш. Полный каталог не является неделимым вариантом.

## Угрозы достоверности

- утечка сведений между вариантами;
- разные исходные коммиты или зависимости;
- разные модели, рассуждения, разрешения или инструменты;
- знание оценщиком варианта;
- неравные критерии приёмки запросов;
- учёт неуспехов только одного варианта;
- использование экономии токенов вместо корректности;
- перенос вывода с учебного примера на production.

Сохраняйте исходные записи для проверки другим разработчиком.

## Интерпретация с учётом модели

Не закрепляйте постоянный вывод за поколением моделей.
Повторите сравнение после существенного изменения модели, стандартного уровня
рассуждений, инструментов или runtime Codex.
Правила проектирования — в [руководстве по навыкам с учётом модели](model-adaptive-skills.md).
