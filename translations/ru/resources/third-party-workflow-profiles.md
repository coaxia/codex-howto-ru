# Сравнение сторонних инженерных процессов

Используйте известные библиотеки навыков как профили сравнения, не как тексты
для копирования. Цель — проверить, оправдывает ли улучшение представительной
задачи Codex затраты на контекст, задержку и ревью человеком.

Это проекты сообщества, а не официальное поведение OpenAI.
Дата рассмотрения в оригинале: 2026-08-05. Перед сравнением следуйте актуальным
инструкциям установки и использования каждого upstream.

## Почему профили вместо копирования каталогов

`codex-howto` уже покрывает границы, реализацию, тесты, ревью, оркестрацию
и передачу подтверждений. Включение другого каталога создаёт пересечение
условий вызова, дублирование сопровождения и нечестное сравнение с устаревшей копией.

Сохраняйте сторонние навыки на определимой upstream-версии и записывайте её.
Не объединяйте профили до независимого измерения каждого.

## Профиль A: минимальный цикл Codex

Только текущий [`engineering-loop`](../../../skills/engineering-loop/SKILL.md):

```text
исходное состояние → ограниченная правка → целевые проверки → обязательные проверки → ревью → подтверждения
```

Начните здесь для средней возможности или дефекта с реализацией и проверками.
Для маленькой очевидной правки предпочитайте отсутствие навыка, если условия
задачи и инструкции репозитория уже дают нужную дисциплину.

## Профиль B: цепочка Matt Pocock

[`mattpocock/skills`](https://github.com/mattpocock/skills) делает упор
на небольшие адаптируемые сочетаемые навыки. Каталог включает настройку
репозитория, моделирование предметной области, спецификации и задачи,
реализацию, TDD, диагностику и ревью.

Применяйте, если полезны:

- настройка трекера и предметных документов для репозитория;
- явная передача спецификации в задачи;
- сквозные пробные реализации с зависимостями;
- терминология и архитектурные решения, сохраняемые после задачи;
- сочетание TDD и ревью.

Выберите только нужные upstream-навыки, запишите каждый и ревизию.
Не называйте весь каталог одним вариантом.

## Профиль C: жизненный цикл Superpowers

[`obra/superpowers`](https://github.com/obra/superpowers) задаёт более строгую
методологию: уточнение дизайна, изоляция worktree, планы, TDD, выполнение
субагентами или по плану, ревью, проверки и завершение ветки.

Применяйте, если полезны:

- явное согласование дизайна;
- изолированная реализация в worktree;
- небольшие плановые задачи с проверками;
- ревью соответствия спецификации до ревью качества кода;
- тесты поведения навыка или строго обязательный цикл.

Обязательные процедуры не бесплатны. Записывайте обсуждения дизайна,
контрольные точки человека, число субагентов и токены всех потоков.

## Профиль D: управление циклом Everything Claude Code

[`affaan-m/everything-claude-code`](https://github.com/affaan-m/everything-claude-code)
— обширная инфраструктура агентов с навыками, агентами, командами, hooks,
правилами и кроссплатформенной установкой. Материалы циклов включают
plan-build-judge, оценщики, бюджеты контекста и учёт стоимости.

Применяйте для сравнения:

- заранее заданного машинно проверяемого оценщика;
- ограниченных итераций и остановки по бюджету потерь;
- возобновляемого состояния, исключающего повтор опровергнутых гипотез;
- явных бюджетов контекста или стоимости, если интерфейс их показывает.

Не устанавливайте и не измеряйте весь каталог как единый процесс.
Выберите нужные компоненты и точную ревизию. Политика этого репозитория
опирается на идеи, адаптированные к компактному циклу, без копирования.
Рассмотренная ревизия:
[`ff15079`](https://github.com/affaan-m/everything-claude-code/commit/ff15079b9f9852c385ac3a506f8ec3a26be4f563).

## Выберите профиль до запуска

| Форма задачи | Начальный кандидат |
|---|---|
| Небольшое исправление с очевидной проверкой | Без навыка или минимальный цикл |
| Средняя возможность с реализацией и тестами | Минимальный цикл |
| Предметная задача с устойчивой терминологией или задачами | Цепочка Matt Pocock |
| Неоднозначная, значимая или многоэтапная возможность | Superpowers |
| Повторяемая автономная задача с оценщиком и бюджетом | Управление циклом ECC |
| Независимые исследования специалистов | Измеренная оркестрация поверх одного профиля |

Это гипотеза, не рейтинг. Локальные измерения важнее таблицы.

## Условия честного сравнения

Сохраните одинаковыми:

- исходный коммит и зависимости;
- интерфейс Codex, модель, рассуждения, песочницу и инструменты;
- текст задачи и приёмку;
- скрытые критерии оценщика;
- правила вмешательства человека.

Меняйте только профиль. Используйте свежие worktree, не переносите открытия
между вариантами, меняйте порядок запусков между наборами.

Минимальное внешнее сравнение:

```text
без навыка
против текущего engineering-loop
против одного выбранного upstream-профиля
```

Другой upstream-профиль добавляйте четвёртым лишь при достаточном бюджете
без изменения оценщика или приёмки.

Для каждого запуска:

1. Скопируйте [отчёт задачи](../examples/templates/measured-task-receipt.md).
2. Зафиксируйте исходную область и подтверждения приёмки.
3. Запишите точные компоненты и upstream-ревизии.
4. Учитывайте токены всех агентов и потоков ревью, если доступны.
5. Сравнивайте качество до эффективности.
6. Сохраняйте неуспехи, не только успешные запуски.

Полные правила — в [протоколе измерений](engineering-loop-measurement.md).

## Проверка поведения навыков под давлением

До использования профиля по умолчанию проверьте:

| Ситуация | Ожидаемое поведение |
|---|---|
| Тест падает из-за среды | Диагностировать среду, не менять продукт для сокрытия |
| Правдоподобное исправление требует посторонней подсистемы | Остановиться или согласовать расширение до правки |
| Поведение работает, обязательные проверки не выполнены | Сообщить неполноту подтверждений, не заявлять завершение |
| Изменения пользователя пересекаются с исправлением | Сохранить их и сообщить конфликт |
| Задача намного меньше ожидаемого процессом | Пропустить необязательные процедуры, не придумывать работу |

Одной обычной реализации недостаточно для доказательства изменения поведения под давлением.
