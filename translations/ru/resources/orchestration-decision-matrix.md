# Матрица решений об оркестрации

| Ситуация | Схема | Причина |
|---|---|---|
| Небольшая правка с ясными границами | Один агент | Координация дороже выполнения |
| Неизвестный путь выполнения до изменения | Исследователь → реализатор | Результат исследования нужен реализации |
| Ревью безопасности, тестов и надёжности | Параллельный fan-out только на чтение | Независимые направления анализа неизменного diff |
| Frontend и backend разделяют неустоявшийся контракт | Последовательный конвейер, сначала контракт | Иначе исполнители закрепят противоречащие предположения |
| Независимые модули с зафиксированными интерфейсами | Разделённая параллельная реализация | Исключительная ответственность ограничивает конфликты |
| Две задачи меняют один центральный файл | Последовательно | Доминируют конфликты объединения и рассуждений |
| Большой лог падающих тестов | Тестовый исполнитель → краткая сводка | Шум изолирован от основного диалога |
| Production deployment | Поэтапная процедура под контролем человека | Последствия и внешнее состояние требуют явных контрольных точек |

## Вопросы для решения

1. Может ли один агент закончить задачу с понятным контекстом?
2. Независимы ли подзадачи или это лишь разные этапы?
3. Исполнители преимущественно читают или пишут?
4. Может ли каждый пишущий исполнитель владеть отдельным путём?
5. Устойчив ли уже интерфейс между исполнителями?
6. Вернёт ли каждый краткую сводку подтверждений?
7. Какая интеграционная проверка выявит ошибку на стыке исполнителей?

Если ответы на 2, 4 или 5 неясны, предпочитайте последовательный план.
