# Критерии ревью практикума

Откройте после первого прохода. Здесь перечислены намеренно внесённые
существенные дефекты; список не исключает другие обоснованные замечания.

## Backend

- `reserve` принимает нулевое и отрицательное количество, хотя контракт требует
  положительного. Отрицательное количество увеличивает доступный запас.
- Исходные тесты покрывают корректное резервирование и недостаток запаса,
  но не эту границу. Регрессионный тест должен упасть до изменения реализации.
- Аккуратное решение также определяет поведение `bool`, поскольку Python
  считает такие значения целыми числами; это вторично относительно внесённого дефекта.

## Frontend

- Поле клиента не имеет программно связанной подписи; placeholder её не заменяет.
- Изменения успеха и ошибки не объявляются вспомогательным технологиям как live status;
  обработка фокуса при ошибке отсутствует.
- `innerHTML` соединяет недоверенный текст клиента с разметкой, допуская
  внедрение HTML или скрипта. Создавайте DOM-узлы или используйте `textContent`.
- Ограничения количества в разметке неполны, хотя JavaScript частично проверяет ввод.

## Инфраструктура

- Образ использует изменяемый тег `latest` вместо проверенной неизменяемой версии или digest.
- Контейнер запускается от root и допускает повышение привилегий.
- Нет readiness/liveness-проверок, запросов ресурсов или ограничений CPU и памяти.
- Не определены rollout, прерывание, мониторинг, откат и целевая среда.
- У примера нет реального образа, аккаунта или кластера.
  Ревью не должно придумывать результат применения или пытаться выполнить deploy.

## Качество ревью

Хороший ответ:

- ссылается на точные файлы и достижимое поведение;
- разделяет последствия для корректности, доступности, безопасности и эксплуатации;
- не выдаёт предпочтения по стилю за дефекты;
- отделяет выполненные проверки от предложенных;
- не заявляет экономию токенов от оркестрации без измерений;
- останавливается после исчерпания заданной области ревью.
