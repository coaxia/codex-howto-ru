# Инженерный практикум

Отработайте навыки на небольшом примере оформления заказа с учётом запасов,
в котором намеренно оставлены ошибки. Используются только стандартная
библиотека Python и статическая HTML-страница. Ничто не подключается к облачному
аккаунту, реестру пакетов или production-сервису.

## Файлы

```text
engineering-playground/
├── AGENTS.md
├── backend/
│   ├── inventory.py
│   └── test_inventory.py
├── frontend/checkout.html
├── infra/deployment.yaml
└── rubric.md
```

В примерах намеренно внесены дефекты корректности, доступности, безопасности
и эксплуатации. Не читайте [критерии ревью](rubric.md) до первого самостоятельного прохода.
Исполняемые файлы берите из [оригинального практикума](../../../../labs/engineering-playground/README.md).

## Первая проба: один backend-дефект

Начните с разделов «Подготовка», «Практикум 1» и «Проверка первой пробы».
Остальные упражнения необязательны: для знакомства с процессом не нужно
проходить весь курс или устанавливать весь каталог навыков.

Нужны локальная копия репозитория, Python 3, Git и уже доступный Codex.
Пять минут — ориентир для настроенной среды, а не измеренная гарантия времени.
Работа Codex может расходовать лимиты аккаунта; сам пример не требует сторонних пакетов.

## Подготовка

Из корня оригинального репозитория `codex-howto` скопируйте практикум
и только навык `engineering-loop` в новую временную директорию.
Глобальные навыки не меняются, пакеты не устанавливаются:

```bash
demo_root="$(mktemp -d)"
cp -R labs/engineering-playground "$demo_root/playground"
mkdir -p "$demo_root/playground/.agents/skills"
cp -R skills/engineering-loop "$demo_root/playground/.agents/skills/"
cd "$demo_root/playground"
git init
git add .
git commit -m "baseline intentionally flawed playground"
pwd
```

Если Git identity не настроена, коммит необязателен; сохраните чистую копию
для сравнения итогового diff.

Запустите backend-тесты без внешних зависимостей:

```bash
python3 -m unittest discover -s backend -p "test_*.py"
```

Изначально они проходят. Это намеренно: набор ещё не покрывает внесённый дефект
обработки граничного значения.

## Практикум 1: регрессия в backend

Откройте директорию, выведенную `pwd`, как новую задачу Codex:

```text
$engineering-loop Изучи контракт резервирования запасов, воспроизведи
непокрытый дефект обработки входных граничных значений, добавь минимальный
регрессионный тест, исправь дефект, выполни обязательные проверки и проведи
ревью итогового diff. Меняй только backend-файлы в этой временной копии.
Не читай rubric.md и не исправляй frontend или инфраструктуру.
```

Убедитесь, что цикл фиксирует падающий регрессионный тест до изменения реализации.

### Проверка первой пробы

- Исходные backend-тесты проходили до правок.
- Новый регрессионный тест упал до изменения реализации.
- После исправления тот же тест и весь backend-набор проходят.
- Итоговый diff затрагивает только backend; прежние тесты не ослаблены.
- Передача результата содержит точные команды, результаты и непроверенные части.

Для первой пробы остановитесь здесь. Если навык не обнаружился или шаг упал,
запишите это как отзыв о первоначальной настройке; не устанавливайте новые
навыки в обход необъяснённого сбоя.
[Отправьте краткий отзыв](../../../../COMMUNITY.md#first-trial-feedback).

Для следующих необязательных упражнений устанавливайте лишь выбранные навыки,
как описано в [модуле 05](../../modules/05-engineering-skills/README.md).

## Практикум 2: frontend и доступность

Откройте `frontend/checkout.html` в браузере, проверьте форму с несколькими
именами и количествами, затем попросите:

```text
$build-frontend Проверь и исправь доступную семантику формы оформления заказа,
объявления статуса и ошибок, небезопасный вывод результата. Сохрани простой
дизайн без зависимостей. Проверь управление клавиатурой и объясни,
какие браузерные проверки выполнить не удалось.
```

Одной визуальной проверки недостаточно для подтверждения работы клавиатуры,
объявлений и обработки недоверенного текста.

## Практикум 3: эксплуатационный план

До разрешения правок запросите план:

```text
$operate-devops Проведи ревью infra/deployment.yaml как локального учебного
примера. Ничего не применяй и не развёртывай. Заполни шаблон безопасности
изменения, укажи риски выполнения и rollout, предложи минимальное усиление
манифеста с командами проверки и отката.
```

Если решите выполнить локальные YAML-правки, явно оставьте все apply/deploy-команды
за границами задачи.

## Практикум 4: независимые ревью

Запустите оба навыка ревью для финального diff:

```text
$review-code Проведи ревью diff практикума относительно исходного коммита.
Начни с замечаний и назови проверки, которые были небезопасны или недоступны.
```

```text
$review-security Проведи анализ угроз для diff и оставшихся примеров практикума.
Проследи ввод, контролируемый атакующим, привилегии выполнения и предположения
о цепочке поставки. Ничего не эксплуатируй и не обращайся к внешним системам.
```

Сравните отчёты: замечания корректности и безопасности могут пересекаться,
но каждое должно объяснять собственные последствия и подтверждения.

## Практикум 5: сравнение оркестрации

Сначала выполните ревью одним агентом и запишите время, суммарные токены,
если интерфейс их показывает, качество замечаний и число повторных попыток.
Затем вызовите:

```text
$orchestrate-engineering Реши, полезно ли делегирование для ревью этого практикума.
Если да, используй минимальный набор специалистов только на чтение,
назначь каждому исключительную область и условие остановки, затем убери
дубли и проверь замечания. Если нет, объясни причину и оставь одного агента.
```

Сравните запуски по [таблице эффективности](../../resources/token-efficiency-scorecard.md).
Параллельная работа не доказывает экономию токенов: измеряйте общую стоимость
и полезные подтверждения.

## Практикум 6: измерить инженерный цикл

Следуйте [протоколу измерений](../../resources/engineering-loop-measurement.md)
с тремя свежими копиями. Передайте `no_skill` условия backend-задачи без навыков;
`full_skill` — те же условия с `engineering-loop` из тега `v0.2.0`;
`lean_skill` — те же условия с текущим `$engineering-loop`.

Запишите три запуска в копию
[`engineering-loop-runs.csv`](../../../../examples/measurements/engineering-loop-runs.csv).
Из корня оригинального репозитория скопируйте запись в доступное для записи место
и подготовьте сводку:

```bash
cp examples/measurements/engineering-loop-runs.csv \
  /tmp/engineering-loop-runs.csv
python3 scripts/summarize_engineering_loop.py \
  /tmp/engineering-loop-runs.csv
```

Повторите frontend- и инфраструктурную задачи до вывода о тенденции.
Не читайте критерии ревью между вариантами.

## Проверка всего практикума — необязательно

- Новый тест падает до backend-исправления и проходит после.
- Frontend-проверка охватывает клавиатуру, подписи, объявления и безопасный вывод, а не только внешний вид.
- Результат по инфраструктуре разделяет план, применение, проверку и откат.
- Ревью кода и безопасности содержат подтверждённые замечания либо явно сообщают об их отсутствии.
- Решение об оркестрации называет выбранные и пропущенные роли.
- Сравнение использует три свежие копии, фиксированные модель и рассуждения,
  критерии качества перед показателями эффективности.
- Ни одна команда не обращалась к реальной среде или внешнему сервису.
