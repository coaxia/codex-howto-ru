# Benchmark оркестрации реагирования на инциденты

Большая задача реализации без зависимостей для сравнения одного агента
с ограниченной оркестрацией нескольких. Она объединяет хранение данных,
валидацию ввода, HTTP-поведение, конкурентную запись, состояние браузера,
доступность, адаптивный интерфейс, автоматические проверки, интеграцию и отчёт.

Используйте её для проверки гипотезы. Оркестрация полезна, только если сокращение
времени или улучшение покрытия оправдывает суммарные токены, конфликты и интеграцию.

## Одинаковые исходные копии

Работайте только во временных копиях [оригинального примера](../../../../labs/incident-response-benchmark/README.md).
Реализации `incident/` и `web/` намеренно отсутствуют, исходные тесты падают.
Из корня оригинального репозитория:

```bash
cd labs/incident-response-benchmark
benchmark_root="$(mktemp -d)"
cp -R AGENTS.md README.md TASK.md test .gitignore "$benchmark_root/"
cd "$benchmark_root"
git init
git add .
git commit -m "baseline incident-response benchmark"
```

Создайте две свежие копии одного коммита. Не включайте `evaluator.py` в кандидат.
Применяйте его только после остановки обоих вариантов:

```bash
python3 /path/to/codex-howto/labs/incident-response-benchmark/evaluator.py \
  /path/to/candidate \
  /path/to/codex-howto/labs/incident-response-benchmark
```

Оценщик выполняет Python-код кандидата и запускает его локальный сервер.
Запускайте его в той же временной песочнице и с теми же разрешениями.
Не проверяйте недоверенный результат на привилегированном хосте.
Браузерные проверки статически проверяют контракт и не заменяют взаимодействие
с браузером или вспомогательными технологиями.

## Зафиксированный контракт компонентов

Контракт достаточно полон для исключительной ответственности.
Не позволяйте исполнителям изобретать несовместимые интерфейсы.

```text
incident/
├── __init__.py
├── server.py       # HTTP adapter and CLI entry point
└── store.py        # validation, transitions, JSON persistence
web/
├── app.js          # browser behavior and API calls
├── index.html
└── styles.css
```

`server.py` — HTTP-адаптер и CLI-вход; `store.py` — валидация, переходы
и JSON-хранение; `app.js` — поведение браузера и вызовы API.

### Контракт хранилища

`incident.store` экспортирует `IncidentStore`, `ValidationError`, `ConflictError`.

- `IncidentStore(path)` читает и записывает JSON-массив по `path`; отсутствие файла означает отсутствие инцидентов.
- `list_incidents(status=None, severity=None)` возвращает сначала недавно обновлённые записи и поддерживает оба фильтра.
- `create(payload)` требует непустой `title` и severity `sev1`, `sev2` или `sev3`.
- Новые инциденты получают уникальный строковый `id`, `status: "open"`,
  целочисленный `version: 1`, timestamps `created_at` и `updated_at` в UTC.
- `update(id, payload)` требует текущую целочисленную `version` вызывающего.
  Устаревшая версия вызывает `ConflictError`.
- Обновление может менять `title`, `severity`, `status`;
  status — `open`, `mitigating` или `resolved`.
- Каждое успешное обновление увеличивает `version`, обновляет `updated_at`, сохраняя `created_at`.
- Запись потокобезопасна, использует временный файл и `os.replace` в директории хранилища.
- Возвращаются безопасные копии: вызывающий не может косвенно изменить сохранённое состояние.

### Контракт HTTP

Запуск приложения:

```bash
python3 -m incident.server --host 127.0.0.1 --port 8080 --data data/incidents.json
```

Все JSON-ответы задают `Content-Type: application/json`.
Неверный JSON или поля возвращают `400`, неизвестный инцидент — `404`,
устаревшая версия — `409`.

| Метод | Путь | Успешный ответ |
| --- | --- | --- |
| `GET` | `/health` | `200 {"status":"ok"}` |
| `GET` | `/api/incidents?status=&severity=` | `200 {"incidents":[...]}` |
| `POST` | `/api/incidents` | `201 {"incident":{...}}` |
| `PATCH` | `/api/incidents/{id}` | `200 {"incident":{...}}` |

Сервер также отдаёт `web/index.html` по `/` и два статических ресурса
под `/web/`. Предотвращайте path traversal: запрошенный путь не должен выходить из `web/`.

### Контракт браузера

- Нативная форма создания с title и severity.
- Инциденты в `#incident-list`: статус, severity и управление переходом open → mitigating → resolved.
- Фильтрация статуса и severity без перезагрузки страницы.
- Состояния запроса, валидации, пустого списка и конфликта в `#message`, являющемся live region.
- Семантические элементы управления, связанные подписи, видимый клавиатурный фокус и адаптивный макет.
- Зафиксированные API-пути и поле версии; без внешних библиотек, шрифтов, изображений и сетевых сервисов.

## Контролируемое сравнение

Сохраните одинаковыми исходный коммит, текст задания, модель, уровень рассуждений,
разрешения, инструменты, лимит времени и оценщик. Меняется только метод:

- `single_agent`: один агент отвечает за реализацию, тесты, ревью и передачу результата;
- `orchestrated`: управляющий агент может назначить backend и frontend разным
  исполнителям с исключительными путями, затем объединяет, проверяет систему,
  проводит ревью и пишет отчёт.

В первом оркестрированном запуске не больше двух исполнителей реализации:
дополнительные не создают новых независимых областей записи.
Управляющий агент отвечает за `benchmark-final.md`; исполнители не меняют одни файлы.

Записывайте приёмку, время, токены всех агентов, число исполнителей,
повторные попытки, конфликты, интеграционные переделки, вмешательства человека
и полноту подтверждений. Недоступную телеметрию помечайте `unavailable`,
не оценивайте приблизительно. До общего вывода повторите запуски или меняйте их порядок.

Первый [пробный запуск](../../../../examples/measurements/incident-orchestration-smoke-2026-08-11.md)
проверил пример и оценщик, но намеренно не делает выводов об эффективности:
варианты пересекались по времени, телеметрия токенов была недоступна.
