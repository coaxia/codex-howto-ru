# 09 · Оркестрация

## Результат

Координируйте инженерную работу нескольких агентов с явными зависимостями,
ответственностью и условиями объединения результатов.

## Обязанности оркестратора

Главный агент сохраняет у себя:

- требования и критерии приёмки;
- граф зависимостей;
- ответственность за файлы или подсистемы;
- решения, затрагивающие нескольких исполнителей;
- интеграцию, разрешение конфликтов и финальную проверку.

Исполнители получают задачи с чёткими границами и возвращают компактные подтверждения.

Используйте [шаблон задач с зависимостями](../../examples/templates/dependency-aware-tickets.md),
если работа должна сохранять понятность между задачами или агентами.
Каждая задача охватывает один вертикальный срез, называет зависимости
и содержит целевую команду проверки.

## Три полезные схемы

### Fan-out / fan-in: распределить и собрать

Выполняйте независимые анализы преимущественно на чтение параллельно,
затем объединяйте результаты:

```text
ревью безопасности ─┐
пробелы в тестах ───┼─> удалить дубли → расставить приоритеты → отчитаться
контракт API ───────┘
```

### Конвейер

Используйте последовательные этапы, когда результат одного нужен следующему:

```text
исследование → план → реализация → тестирование → ревью
```

### Разделённая реализация

Распараллеливайте запись только при исключительной ответственности:

```text
worker A: packages/contracts/**
worker B: services/api/**
worker C: apps/web/**
```

Сначала зафиксируйте общие интерфейсы. Если исполнителям нужен один файл,
работайте последовательно.

## Протокол оркестрации

1. Задайте критерии приёмки.
2. Постройте зависимости.
3. Выберите одного агента, конвейер или fan-out.
4. Назначьте исключительные области работы и уровни разрешений.
5. Требуйте сводки подтверждений.
6. Ожидайте результаты в явно заданных точках объединения.
7. Интегрируйте в порядке зависимостей.
8. Выполните проверки уровня системы.
9. Проведите ревью общего diff.

## Контроль сбоев

- Остановите исполнителя, расширяющего задачу.
- Пересмотрите план, если изменилось предположение о зависимости.
- Не превращайте непроверенное утверждение одного исполнителя в требование для другого.
- В спорных или рискованных областях предпочитайте исполнителей только на чтение.
- Записывайте нерешённые вопросы в основном диалоге.

## Упражнение

Установите [`orchestrate-engineering`](../../../../skills/orchestrate-engineering/SKILL.md),
выполните [запрос на оркестрированное ревью](../../examples/prompts/orchestrated-review.md),
затем сравните результат с одним проходом `/review`.
Для сравнения реализаций с исключительными областями записи и системным
оценщиком используйте [benchmark реагирования на инциденты](../../labs/incident-response-benchmark/README.md).

```bash
mkdir -p .agents/skills
cp -R /path/to/codex-howto/skills/orchestrate-engineering .agents/skills/
```

Измеряйте:

- уникальные ценные замечания;
- дубли;
- ложные срабатывания;
- затраченное время;
- общее число агентов;
- суммарные токены, кредиты или стоимость, если интерфейс их показывает;
- читаемость основного контекста.

## Проверка

- Выбранная схема соответствует реальным зависимостям.
- У каждого участка записи единственный владелец.
- Финальные проверки охватывают межмодульное поведение.
- Объединённый результат удовлетворяет исходным критериям приёмки.
- Заявление об эффективности связано с измеренными качеством, временем,
  ясностью контекста, повторными попытками или общей стоимостью.
- Сохраняемые задачи фиксируют зависимости, ответственность и проверки
  без копирования всей спецификации в контекст каждого исполнителя.
