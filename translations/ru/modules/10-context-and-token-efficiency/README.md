# 10 · Эффективность контекста и расхода токенов

## Результат

Используйте контекст для решений и подтверждений вместо повторных инструкций,
широких обходов репозитория и сырых логов.

## Основной принцип

Несколько агентов обычно расходуют больше токенов суммарно, чем сопоставимый
запуск одного агента. Используйте их для сокращения времени, изоляции шумного
исследования или более полного предметного анализа, а не как способ экономить токены.

## Иерархия контекста

1. **Запрос:** текущая цель и ограничения.
2. **`AGENTS.md`:** устойчивые факты репозитория.
3. **Метаданные навыка:** компактное описание для выбора процесса.
4. **`SKILL.md`:** выбранная процедура.
5. **Справочные материалы:** подробности, загружаемые по необходимости.
6. **Поток субагента:** изолированная шумная работа.
7. **Сводка:** выжимка подтверждений для основного диалога.

Помещайте информацию на самый экономный устойчивый уровень, с которого она
всё ещё доступна для задачи.

## Приёмы повышения эффективности

### Сначала задайте направление чтения

Укажите точки входа, падающие команды и вероятные ответственные модули.
Просите Codex прослеживать цепочки вызовов вместо просмотра всех файлов.

### Загружайте подробности по необходимости

Держите основные тексты навыков короткими. Варианты для фреймворков, чек-листы
и схемы размещайте в непосредственно связанных справочных файлах.

### Предпочитайте целевые проверки

Сначала выполняйте минимальный воспроизводящий тест, затем обязательные широкие
проверки. Не передавайте полный тестовый лог монорепозитория в основной диалог,
если исполнитель может вернуть список упавших случаев.

### Подкрепляйте сводки подтверждениями

Полезная сводка исполнителя содержит:

- вывод;
- подтверждение файлом или командой;
- неопределённость;
- рекомендуемый следующий шаг.

### Сжимайте контекст на границах этапов

После исследования или отладки повторите подтверждённые факты и уберите
опровергнутые версии перед реализацией.

При передаче работы другому человеку, задаче или контекстному окну используйте
[шаблон передачи инженерного результата](../../examples/templates/engineering-handoff.md).
Переносите решения, подтверждения, неудачные подходы, риски и следующий шаг,
который даст новые подтверждения, вместо всего диалога.

### Избегайте повторных попыток без диагностики

Если команда дважды упала по одной причине, остановитесь и проверьте среду,
разрешения или предположение, а не запускайте её вслепую снова.

## Неудачные подходы

- установка десятков пересекающихся навыков;
- копирование руководств фреймворков в `AGENTS.md`;
- требование каждому исполнителю читать весь репозиторий;
- возврат сырых логов вместо выводов;
- высокий уровень рассуждений для механических правок;
- параллельная работа агентов над одним файлом;
- сохранение устаревших требований в активном диалоге.

## Упражнение

Заполните [таблицу оценки эффективности](../../resources/token-efficiency-scorecard.md)
для реальной задачи. Чтобы оценить влияние инженерного цикла на результат,
выполните [протокол парного измерения](../../resources/engineering-loop-measurement.md).
Сначала сравнивайте критерии качества, затем повторные попытки, шум контекста,
время или число токенов.

## Проверка

- Основной контекст содержит требования, решения и результаты.
- Повторно используемые инструкции не дублируются в запросах.
- Каждый делегированный результат меньше рабочего контекста исполнителя.
- У дополнительных агентов есть измеримая причина существования.
- Передача результата достаточно компактна для повторной загрузки и сохраняет решения и подтверждения.
