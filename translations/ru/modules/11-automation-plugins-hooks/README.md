# 11 · Автоматизация, плагины и hooks

## Результат

Превратите устойчивые процессы в расширения Codex, которые можно распространять
или использовать для обязательных проверок.

## Путь развития

```text
запрос → AGENTS.md → навык → плагин → автоматизация
                       ↘ hook для механических проверок
```

Используйте:

- **навык** для повторяемой процедуры;
- **плагин** для распространения навыков, при необходимости с hooks, приложениями или MCP-конфигурацией;
- **hook** для детерминированных проверок жизненного цикла;
- **автоматизацию** для устойчивой периодической или автономной работы;
- `codex exec` для неинтерактивного CI и скриптов.

## Когда процесс готов к автоматизации

- Вход и выход заданы явно.
- Поведение при сбое понятно.
- Разрешения ограничены.
- Процесс многократно успешно выполнялся интерактивно.
- Результат проверяется машиной.
- Для существенных записей предусмотрено ревью человеком.

## Hooks

Hook должен обеспечивать узкий механический инвариант: например, запуск
форматтера или запрет определённого шаблона файлов. Скрипты hook должны быть
детерминированными, быстрыми и безопасными при повторном запуске.

Не прячьте сложный агентный процесс внутри hook.
Не выполняйте недоверенный текст как shell-код.

## Плагины

Плагину обязателен `.codex-plugin/plugin.json`; он может включать навыки,
hooks, приложение на базе MCP, конфигурацию и ресурсы.
Создавайте плагин, когда процесс достаточно устойчив для распространения
за пределы одного репозитория.

## Схема CI

1. Начните с анализа только на чтение.
2. Используйте отдельный токен с минимальными правами.
3. Задайте явный timeout или бюджет.
4. Выдавайте результат, который можно проверить.
5. При необходимости нового согласования завершайте работу без опасного продолжения.
6. Оставляйте решения о merge и deploy под действием правил репозитория.

## Практикум A: упаковать и установить локальный плагин

Репозиторий содержит минимальный marketplace и плагин:

```text
examples/plugin-marketplace/
├── .agents/plugins/marketplace.json
└── plugins/engineering-review/
    ├── .codex-plugin/plugin.json
    └── skills/evidence-review/SKILL.md
```

Из корня репозитория:

```bash
codex plugin marketplace add ./examples/plugin-marketplace
codex plugin marketplace list
codex plugin list --marketplace codex-howto-lab --available --json
codex plugin add engineering-review@codex-howto-lab
```

Начните новую задачу и вызовите `$evidence-review` для небольшого локального diff.
Затем удалите учебную установку:

```bash
codex plugin remove engineering-review@codex-howto-lab
codex plugin marketplace remove codex-howto-lab
```

Изучите манифест до установки. Перед распространением реальному плагину нужны
устойчивое версионирование, данные издателя, тесты и политика обновления.

## Практикум B: настроить hook и проверить доверие

Работайте во временном клоне без существующего `.codex/hooks.json`.
Скопируйте hook проверки:

```bash
mkdir -p .codex
cp examples/hooks/validate-on-stop/hooks.json .codex/hooks.json
```

Запустите Codex, откройте `/hooks`, изучите точную команду и источник.
Доверяйте hook только после проверки, что он запускает
`scripts/validate_repo.py` этого репозитория в режиме чтения.
Выполните задачу только по документации и убедитесь, что Stop hook сообщает о проверке.

Измените один безобидный символ в копии hook, перезапустите Codex и убедитесь,
что новый hash требует повторного рассмотрения. Восстановите или удалите копию
после практикума. Не заменяйте и не объединяйте существующую конфигурацию hooks
без проверки каждого обработчика.

## Практикум C: запланировать автоматизацию только на чтение

Сначала вручную выполните [запрос на поиск расхождений документации](../../examples/prompts/scheduled-docs-drift.md).
В приложении Codex создайте временную периодическую автоматизацию с этим
запросом и репозиторием, используя короткое тестовое расписание.

Проверьте первый запуск:

- он остаётся только на чтение;
- у каждого расхождения есть место в локальном файле и официальный источник;
- недоступность документации сообщается явно, без догадок;
- ответ об отсутствии подтверждённых расхождений краток.

Отключите или удалите временную автоматизацию после проверки.
Добавляйте запись только после устойчивых повторных запусков на чтение
и определения точки согласования человеком.

## Практикум D: неинтерактивный CI

Превратите один ручной чек-лист ревью в:

1. Навык, вызываемый явно в локальном Codex.
2. Проверку `codex exec` только на чтение в тестовой ветке.
3. Документированный откат, удаляющий шаг CI.

Не добавляйте автоматические исправления, пока результаты чтения ненадёжны.

## Проверка

- Без учётных данных процесс завершается безопасно.
- CI не может менять production или защищённые ветки.
- Локальный плагин устанавливается, вызывается и удаляется корректно.
- Команда hook и hash доверия проверены до выполнения.
- Периодическая задача доказанно работает только на чтение и удалена после практикума.
- Удаление hook, плагина, автоматизации и CI документировано и обратимо.
- Люди-ревьюеры могут изучить полученные подтверждения.
