# 07 · Тестирование и ревью

## Результат

Потребуйте от Codex подтверждения работоспособности изменения и ревью существенных дефектов.

## Инженерный цикл

```text
воспроизвести → реализовать → целевой тест → обязательные проверки → изучить diff → ревью → отчёт
```

Слово «реализовано» не означает завершения. Задайте команды и поведение,
которые подтверждают требуемый результат.

Установите [`engineering-loop`](../../../../skills/engineering-loop/SKILL.md),
чтобы повторно использовать этот цикл для задач полного внедрения.
Навыки реализации, тестирования, ревью и безопасности дают более узкие предметные инструкции.

## Тестируйте с учётом риска

Приоритеты:

1. Изменяемое поведение, видимое пользователю.
2. Граничные случаи и сбои.
3. Инварианты авторизации и целостности данных.
4. Интеграционные контракты.
5. Широкие наборы регрессионных тестов.

Избегайте тестов, просто повторяющих детали реализации.

## Сначала замечания ревью

Полезное ревью ищет:

- ошибки корректности и риски регрессии;
- проблемы безопасности и авторизации;
- потерю данных и проблемы миграции;
- ошибки конкурентного выполнения и ветвей отказа;
- отсутствие содержательных тестов.

Каждое замечание должно содержать место, последствия, подтверждение или путь
воспроизведения и минимальное безопасное направление исправления.
Предпочтения по стилю не должны вытеснять реальные дефекты.

## Разделяйте контекст автора и ревьюера

Для рискованных изменений используйте новый проход ревью или агента-ревьюера
с доступом только на чтение. Он должен изучить фактический diff и правила
репозитория, а не только пересказ автора.

## Упражнение

Используйте намеренно внесённый backend-дефект в
[инженерном практикуме](../../labs/engineering-playground/README.md)
или аналогичный временный пример:

1. Установите `test-software`, подходящий навык реализации, `review-code` и `review-security`.
2. С помощью `$test-software` напишите падающий регрессионный тест.
3. Исправьте дефект с подходящим навыком реализации.
4. Выполните целевые и обязательные широкие проверки.
5. Вызовите `$review-code` для полученного diff.
6. Независимо используйте `$review-security` для анализа границ доверия и ввода, контролируемого атакующим.
7. Согласуйте пересекающиеся замечания, сохраняя различие между последствиями для корректности и безопасности.

## Проверка

- Тест падает на исходном поведении.
- После исправления тест проходит.
- Обязательные lint-, type- и build-проверки проходят.
- Замечания ревью исправлены или явно приняты.
- Для замечаний безопасности есть достижимый путь атаки либо они отмечены как дополнительная защита.
- Итоговый отчёт отделяет проверенные результаты от невыполненных проверок.
