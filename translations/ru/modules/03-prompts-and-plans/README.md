# 03 · Запросы и планы

## Результат

Превратите расплывчатую просьбу в инженерную задачу с ясными границами.

## Запрос из четырёх частей

```text
Цель: наблюдаемое изменение.
Контекст: нужные файлы, ошибки, макеты или задачи.
Ограничения: архитектура, безопасность, совместимость и границы работы.
Завершено, когда: выполнены команды и проверено поведение, подтверждающие результат.
```

Пример:

```text
Цель: отклонять просроченные токены сброса пароля в существующем формате ошибок API.
Контекст: начни с src/auth/reset.ts и тестов его маршрута.
Ограничения: сохрани публичные поля ответа; не добавляй зависимости.
Завершено, когда: тест просроченного токена падает до изменения и проходит после,
а целевой набор тестов аутентификации и проверка типов проходят.
```

## Когда сначала нужен план

Используйте режим планирования, если:

- требования неоднозначны;
- затронуты несколько подсистем;
- есть миграция или граница совместимости;
- изменение трудно отменить;
- вы пока не можете назвать команды проверки.

Попросите включить в план предположения, затронутые интерфейсы, этапы реализации,
проверки и откат.

Не превращайте небольшую понятную правку в церемонию. План полезен, когда
снижает вероятность выполнения неверной работы.

Если для изменения нужен сохраняемый документ для ревью, скопируйте
[шаблон инженерной спецификации](../../examples/templates/engineering-spec.md).
Он разделяет подтверждённые требования, открытые вопросы, затронутые контракты,
проверки, безопасность поставки и явные исключения из объёма задачи.

## Направляйте поиск контекста

Укажите Codex вероятные точки входа вместо передачи всего репозитория.
Просите расширять контекст только при необходимости изучить импорты,
вызывающий код, тесты или контракты.

Полезные ориентиры:

- падающий тест или stack trace;
- модуль, отвечающий за поведение;
- похожая реализация;
- публичный контракт или схема;
- команда воспроизведения проблемы.

## Упражнение: вопросы до реализации

Предложите Codex намеренно неполную идею:

```text
Хочу добавить API-ключи уровня организации. Пока не реализуй.
Задавай вопросы, пока права, жизненный цикл, хранение, аудит, совместимость
и критерии приёмки не станут конкретными. Затем подготовь поэтапный план
с рисками и командами проверки.
```

## Проверка

- План отделяет подтверждённые требования от предположений.
- У каждого этапа есть подтверждение завершения.
- Указаны риски безопасности и миграции.
- План достаточно короткий, чтобы проверить его до написания кода.
- Если нужна сохраняемая спецификация, она отделяет факты от предположений
  и называет наблюдаемые проверки.
